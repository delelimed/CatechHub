1. Architettura del bootstrap

L'applicazione esegue un bootstrap sequenziale in 6 fasi (main.dart), ciascuna con initializzazione bloccante e propagazione errori. La funzione main() coordina il flusso tramite AsyncNotifierProvider:

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await runZonedGuarded(() async {
    final bootstrap = BootstrapService();
    await bootstrap.phase0();  // Binding Flutter
    await bootstrap.phase1();  // Servizi Dart (Clock, Logger, PathProvider)
    await bootstrap.phase2();  // Hive init + auto-recovery
    await bootstrap.phase3();  // Apertura Box con corruption recovery
    await bootstrap.phase4();  // Analytics / Privacy
    await bootstrap.phase5();  // Servizi aggiornamenti
    await bootstrap.phase6();  // runApp
  }, _fatalErrorHandler);
}

2. Hive Database Layer

2.1 Box e modelli

I dati sono organizzati in 13 box Hive cifrati (HiveAesCipher), aperti sequenzialmente nel bootstrap. Ogni box contiene record serializzati come mappe JSON (Map<String, dynamic>). I modelli Dart espongono toMap()/fromMap() per la serializzazione.

2.2 Identificatori

Ogni record ha un id univoco (stringa, generata via LocalDatabase.newId()). La classe SchoolClass (anagrafica gruppo) possiede inoltre un uniqueCode: stringa di 40 cifre decimali, generata via Random.secure() e persistita nel box alla creazione della classe. Questo codice identifica la classe in modo stabile anche dopo un ripristino da backup o una sincronizzazione P2P, ed è utilizzato come riferimento nelle associazioni P2P tra catechisti.

  • Generazione: generateClassUniqueCode() in class_model.dart — 40 cifre da Random.secure().
  • Backfill: ClassesRepository.ensureUniqueCodes() — assegna un codice a ogni classe che ne è sprovvista (classi precedenti all'introduzione del campo). Chiamato all'avvio dell'app dopo il login.
  • Persistenza: il campo uniqueCode è serializzato in toMap()/fromMap(); se assente nei dati esistenti (null o vuoto), fromMap() restituisce stringa vuota (nessuna auto-generazione al caricamento).

2.3 Indici di sincronizzazione

Per ogni box syncabile, HiveSyncEngine.buildLocalIndex() costruisce un indice con timestamp di modifica e checksum SHA-256 per ogni record. L'indice viene serializzato come SyncIndexEntry e scambiato tra dispositivi durante il sync differenziale. Il campo isDeleted in SyncIndexEntry tiene traccia delle cancellazioni per la propagazione CRDT tra dispositivi.

3.4 HKDF — Session Key derivation

final HKDF_INFO = 'CatechHub_SessionKey_v2';
// info = HKDF_INFO + deviceIdA + deviceIdB (UTF-8 encoded)

Dopo lo scambio ECDH, il shared secret viene derivato tramite HKDF con SHA-256 per produrre la chiave di sessione AES-256-GCM. L'info string include gli ID dei due dispositivi per garantire chiavi uniche per coppia di dispositivi.

3.5 Legacy CBC fallback

Per compatibilità con i pacchetti v1 (prime versioni dell'app), EncryptionService implementa un fallback su AES-256-CBC con padding PKCS7. Il campo "alg": "AES-256-CBC" nel JSON del pacchetto determina l'uso del fallback.

4. Sync Engine (P2P Sync)

CatechHub implementa due canali di sincronizzazione paralleli: Nearby P2P (real-time via Bluetooth/WiFi Direct) e QR Code (offline/on-demand).

4.1 Nearby P2P Sync

Utilizza Google Nearby Connections API con Strategy.P2P_CLUSTER, garantendo che zero dati transitino su internet — solo Bluetooth o WiFi Direct. Il servizio è implementato in P2PSyncService (singleton) con un protocollo a 7 fasi:

Sync differenziale: Entrambi i lati costruiscono un indice locale (HiveSyncEngine.buildLocalIndex()) con timestamp e checksum per record. Ogni dispositivo calcola cosa gli serve dal remoto e cosa il remoto necessita da esso. I record vengono scambiati in modo bidirezionale fino al completamento (tracciato da una macchina a stati: idle → sentIndex → sendDone → receiveDone → complete).

Sync continua in background: All'avvio, se esistono associazioni, il servizio avvia advertising + discovery + sync periodico (ogni 60s). Ascolta le modifiche locali su Hive (debounce 500ms) e invia richieste di sync incrementali. Riconnessione automatica ogni 5 secondi per dispositivi noti. Un indicatore a pallino (8px) nell'app bar mostra lo stato (rosso=nessuna associazione, giallo=associazioni presenti, verde=sync in corso, ciano=dati aggiornati).

Stati: 12 stati di sincronizzazione tracciati da P2PSyncStatus (idle, pairing, discovering, advertising, handshakeSent, handshakeReceived, pairingVerification, sessionEstablished, syncing, completed, error).

4.1.6 Consent Protocol

Role-based auth flow. P2PSyncRole ha tre valori: mioDispositivo, altroCatechista, responsabile. Il flusso di autenticazione differisce in base al ruolo:

  • mioDispositivo: accetta automaticamente le richieste di autenticazione senza intervento dell'utente.
  • altroCatechista: richiede una conferma esplicita dell'utente tramite dialogo prima che la connessione proceda.
  • Entrambi i dispositivi altroCatechista: richiedono un dialogo di permesso sessione su entrambi i dispositivi prima che la connessione venga accettata.

Protocollo di consenso (double opt-in). Quando entrambi i dispositivi hanno ruolo altroCatechista, _onConnectionInitiated verifica _sessionSyncAllowed prima di accettare la connessione in arrivo. Se il consenso non è stato concesso (l'utente non ha premuto "Procedi"), la connessione viene rifiutata con un messaggio di log. Questo garantisce che entrambi gli utenti debbano premere esplicitamente "Procedi" prima di qualsiasi scambio di dati, implementando un meccanismo di double opt-in.

Correzione propagazione ruolo. _pendingHandshakeRemoteRole viene ora correttamente propagato da _pendingHandshakeData durante il flusso di associazione QR. Questa propagazione avviene in due punti chiave:

  • completePairingAfterQrScan — dopo la scansione e decodifica del QR, il ruolo remoto viene estratto dal payload di handshake e salvato nello stato pendente.
  • _handleReadyForVerification — durante l'handshake di verifica dopo la conferma del pairing code, assicurando che remoteRole sia correttamente salvato nell'associazione P2PDeviceAssociation.

Questa correzione garantisce che il ruolo del dispositivo remoto sia registrato accuratamente nel record di associazione, fondamentale per applicare correttamente l'autorizzazione basata sui ruoli nelle sessioni di sincronizzazione successive.

Dialogo di conferma in _handleAuthResponse. Il dialogo di conferma per i dispositivi altroCatechista ora appare anche quando il dispositivo altroCatechista è l'iniziatore della sincronizzazione. In precedenza, il dialogo appariva solo quando il dispositivo altroCatechista era il ricevente. Questo garantisce un consenso simmetrico: indipendentemente da quale dispositivo avvia la connessione, entrambe le parti vengono invitate a confermare prima che la sessione proceda.

4.2 QR Code Sync

Canale alternativo per dispositivi senza Bluetooth o per trasferimenti one-shot. Implementato in QRDataService:

  • Cifratura: AES-256-GCM con PIN a 8 cifre generato via Random.secure(), valido 3 minuti. Derivazione chiave con PBKDF2-HMAC-SHA256 a 12.000 iterazioni (ridotto per performance QR).
  • Chunking: Payload diviso in chunk JSON di max 1200 caratteri, ognuno con checksum SHA-256 (prime 4 cifre esadecimali).
  • Integrità: Checksum SHA-256 dell'intero payload (prime 12 cifre hex) verificato dopo il riassemblaggio.
  • Sync differenziale: buildDatabaseIndex() crea un indice per modulo. computeDiffExport() confronta l'indice locale con quello remoto e trasferisce solo i record nuovi/modificati (risoluzione conflitti: local wins).
  • Moduli supportati: Anagrafica, Presenze, Programmazione, Documenti, Note contatto, Catechesi, Annotazioni giornaliere.

4.3 P2P Security Service

Il modulo P2PSecurityService fornisce le fondamenta crittografiche per tutte le comunicazioni P2P:

  • Scambio chiavi: X25519 (Curve25519) tramite pacchetto cryptography. Ogni dispositivo genera una coppia di chiavi identità long-lived più una coppia per ogni dispositivo associato (chiavi per dispositivo salvate nell'associazione).
  • Derivazione chiave di sessione: HKDF con HMAC-SHA256 (output 32 byte) combinando: shared secret statico + shared secret effimero ECDHE + nonce di handshake (32 byte). Info string: "CatechHub_P2P_Session_v2" + ID dispositivo remoto + ruolo (initiator/responder).
  • Cifratura payload: AES-256-GCM con nonce 12 byte. Wrapper P2PEncryptedPayload con nonce, ciphertext, MAC (128-bit) e tag algoritmo (supporta chacha20-poly1305 come opzione futura).
  • Forward secrecy: Il componente ECDHE effimero è mescolato nell'input HKDF — la compromissione della chiave statica non compromette le chiavi di sessione passate.
  • Pairing code: Codice a 6 cifre decimali derivato da SHA-256 dello shared secret ECDH calcolato da computePairingCode(). Entrambi i dispositivi calcolano lo stesso codice — l'utente verifica visivamente che i codici corrispondano prima di confermare il pairing, prevenendo attacchi Man-in-the-Middle.
  • Key pinning: Alla riconnessione, la chiave pubblica remota deve corrispondere all'associazione salvata (publicKeyMatchesAssociation()). Se la chiave pubblica ricevuta via radio differisce da quella salvata, viene sollevato un allarme MitM e la connessione viene interrotta.
  • Associazioni per dispositivo: Ogni associazione (P2PDeviceAssociation) contiene ora anche devicePrivateKeyBase64 e devicePublicKeyBase64, permettendo chiavi crittografiche uniche per ogni coppia di dispositivi.
  • Associazioni: Valide 30 giorni, salvate in FlutterSecureStorage con prefisso p2p_assoc_.
  • Sessione: Valida max 30 minuti (P2PSession.isValid).
  • Seed crittografico: Random.secure() di Dart per tutti i nonce e salt.

4.4 Sync Status Indicator

Un indicatore visivo a pallino (8px) nell'app bar mostra lo stato della sincronizzazione P2P con codifica a colori:

  • ● Rosso — nessuna associazione o sync non recente
  • ● Giallo — associazioni presenti ma dati non aggiornati
  • ● Verde — sync in corso
  • ● Ciano — dati aggiornati e sync recente confermato

4.5 QR Code package format

{
  "v": 2,
  "encryptedData": "<base64>",
  "totalChunks": N,
  "checksum": "<SHA-256 first 12 hex>"
}

// Each chunk:
{"i": 0, "t": 3, "d": "<base64 data>", "c": "<chunk checksum 4 hex>"}

I pacchetti QR usano un formato simile ma con chunking automatico. Ogni chunk contiene checksum individuale (prime 4 cifre SHA-256). Il PIN a 8 cifre ha validità 3 minuti. Derivazione chiave: PBKDF2-HMAC-SHA256 a 12.000 iterazioni (fast share).

5. Security architecture

5.1 Hardware-backed Master Key (AndroidKeyStore) — SecurityManager

A partire dalla versione 2.0, CatechHub richiede esclusivamente protezione hardware per la chiave master di cifratura Hive. Il modulo SecurityManager (singleton in lib/core/security/security_manager.dart):

  • Verifica la presenza di TEE (Trusted Execution Environment) o StrongBox all'avvio tramite local_auth (biometria come proxy TEE) e FlutterSecureStorage (test scrittura/lettura Keystore)
  • Genera la chiave master AES-256 tramite Hive.generateSecureKey() e la custodisce in AndroidKeyStore con encryptedSharedPreferences=true
  • Se TEE/StrongBox non è disponibile, solleva HardwareSecurityException e blocca l'avvio con SecurityBlockScreen — l'app non si avvia su dispositivi senza hardware di sicurezza
  • Nessun fallback software: la chiave master non viene mai memorizzata in memoria volatile o storage non protetto
  • Flusso di inizializzazione: (1) verifica biometrica (local_auth) → proxy TEE, (2) test FlutterSecureStorage → verifica Keystore, (3) generazione/lettura Master Key, (4) creazione HiveAesCipher, (5) marcatura hardware come verificato

Configurazione Android (flutter_secure_storage): encryptedSharedPreferences: true forza l'uso di KeyGenParameterSpec con setIsStrongBoxBacked(true) su API 28+. StrongBox richiede hardware dedicato (Pixel 3+, Samsung S20+), TEE è presente su quasi tutti i dispositivi Android 10+ certificati.

5.2 freeRASP

Libreria di runtime application self-protection (RASP) che rileva 8 categorie di minacce:

CategoriaRilevamento
Root / Magisk / KernelSUSuperuser binary, mount namespace, SELinux
EmulatorBuild fingerprint, QEMU drivers, Goldfish CPU
App IntegrityFirma APK modificata, debug build
Hooking / Frida / XposedLibrerie di hooking, classLoader injection

Configurazione: killOnBypass = false (l'utente riceve una schermata di blocco personalizzata SecurityBlockScreen ma non viene forzato alla chiusura).

5.3 Auth — local_auth

Authentication auth = Authentication();
bool canAuth = await auth.canCheckBiometrics || await auth.isDeviceSupported();
// biometricOnly = false → fallback a PIN/Pattern/Password del dispositivo

La sessione vive esclusivamente in RAM: nessun token persistito. Il timeout background è di 120 secondi. Allo scadere, la sessione viene invalidata e l'utente deve riautenticarsi.

L'autenticazione locale serve anche come proxy per verificare la presenza di TEE (Trusted Execution Environment) durante il bootstrap di SecurityManager.
