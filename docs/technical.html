1. Architettura del bootstrap

L'applicazione esegue un bootstrap sequenziale (main.dart) con inizializzazione bloccante e propagazione errori: binding Flutter, inizializzazione freeRASP (sicurezza runtime, prima di qualsiasi storage), servizi Dart, Hive.initFlutter() con auto-recovery, apertura dei box con corruption recovery per-box, applicazione delle opzioni native di privacy (FLAG_SECURE) e runApp() con ProviderScope. La funzione main() coordina il flusso tramite AsyncNotifierProvider:

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await runZonedGuarded(() async {
    // FASE 0   — Binding Flutter
    // FASE 0.5 — freeRASP (SecurityService.init, prima di Hive/runApp)
    //           — Hive.initFlutter() + retry su file .lock residui
    //           — LocalDatabase.init(): apertura box con corruption recovery
    //           — Servizi Flutter (date, aggiornamenti) + opzioni privacy native
    // FASE N   — runApp() con Riverpod ProviderScope
  }, _fatalErrorHandler);
}

2. Hive Database Layer

2.1 Box e modelli

I dati sono organizzati in 27 box Hive cifrati (HiveAesCipher con chiave master in AndroidKeyStore TEE/StrongBox via SecurityManager), aperti in LocalDatabase.init() con recovery atomica per-box (_openBoxWithRecovery → deleteBoxFromDisk + ricreazione vuota; solo registroBox è critico e blocca l'avvio su fallimento, LocalDatabase:294). Ogni box contiene record Map<String,dynamic>; i modelli espongono toMap()/fromMap(). Box: registroBox, classes_box, students_box, planning_box, attendance_box, documents_box, document_deliveries_box, attachments_box, contact_notes_box, catechesi_box, meeting_catechesi_box, student_daily_notes_box, trusted_devices_box, meeting_notifications_box, avvisi_box, sync_conflicts_box, parish_config_box, audit_log_box, aula_box, tombstone_box, historical_records_box, catechists_box, class_channel_keys_box, class_channel_ciphertext_box, parish_events_box, substitute_delegations_box, substitute_lesson_notes_box.

2.2 Identificatori

Ogni record ha un id univoco (stringa, generata via LocalDatabase.newId()). La classe SchoolClass (anagrafica gruppo) possiede inoltre un uniqueCode: stringa di 40 cifre decimali, generata via Random.secure() e persistita nel box alla creazione della classe. Questo codice identifica la classe in modo stabile anche dopo un ripristino da backup o una sincronizzazione P2P, ed è utilizzato come riferimento nelle associazioni P2P tra catechisti.

  • Generazione: generateClassUniqueCode() in class_model.dart — 40 cifre da Random.secure().
  • Backfill: ClassesRepository.ensureUniqueCodes() — assegna un codice a ogni classe che ne è sprovvista (classi precedenti all'introduzione del campo). Chiamato all'avvio dell'app dopo il login.
  • Persistenza: il campo uniqueCode è serializzato in toMap()/fromMap(); se assente nei dati esistenti (null o vuoto), fromMap() restituisce stringa vuota (nessuna auto-generazione al caricamento).

2.3 Indici di sincronizzazione

Per ogni box syncabile, HiveSyncEngine.buildLocalIndex() costruisce un indice con timestamp di modifica e checksum SHA-256 per ogni record. L'indice viene serializzato come SyncIndexEntry e scambiato tra dispositivi durante il sync differenziale. Il campo isDeleted in SyncIndexEntry tiene traccia delle cancellazioni per la propagazione CRDT tra dispositivi.

Dopo lo scambio TripleDH (static↔static + static↔ephemeral×2 + ephemeral↔ephemeral, P2PSecurityService.computeForwardSecretKey:834 — forward secrecy, efimere MAI persistite), lo shared secret è HKDF-SHA256 (RFC 5869, output 32B) con info CatechHub_P2P_Session_v3:<ids>:<windowId> + nonce concordato (combinazione ordinata dei due nonce 16B). Deriva sia la chiave di sessione AES-256-GCM (AAD CatechHub_Context_P2P_v1) sia il nonce di sessione. Rotazione ogni 30 min (sessionKeyRotation), heartbeat 30s, revoche e tombstone propagate ad ogni sync.

3.5 Rimozione del formato legacy (v1)

Il formato legacy v1 (AES-256-CBC senza MAC, KDF a singola iterazione) è stato rimosso: i pacchetti v1 non sono più accettati in lettura. Accettarli sarebbe una porta di downgrade che indebolisce la derivazione della chiave e perde l'integrità autenticata del ciphertext (padding oracle). decryptData rifiuta esplicitamente i pacchetti con v != 2.

4. Sync Engine (P2P Sync)

CatechHub implementa due canali di sincronizzazione paralleli: Nearby P2P (real-time via Bluetooth/WiFi Direct) e QR Code (offline/on-demand).

4.1 Nearby P2P Sync — modalità normale reingegnerizzata

Utilizza Google Nearby Connections API con Strategy.P2P_CLUSTER (log in P2PSyncService:319 — zero dati su internet, solo Bluetooth/WiFi Direct). Singleton P2PSyncService + handler NormalModeSyncHandler (lib/features/sync/normal/normal_mode_sync_handler.dart:1, NOP in responsabile). Flusso normale:

  • Mio Dispositivo: condivide sempre catechistId (in p2p_identity cifrato) → se ricevente fresco adotta l'id → sync di tutte le classi, lavoro offline indipendente + realtime quando vicini.
  • Altro Catechista: associa atomico a classi condivise (catechistIds/associatedCatechistIds/catechistRoles/catechistDeviceCounts) → sync solo classi condivise + _performBidirectionalSync immediato cifrato.

4.1.6 Consent Protocol

Role-based auth flow. P2PSyncRole ha tre valori: mioDispositivo, altroCatechista, responsabile. Il flusso di autenticazione differisce in base al ruolo:

  • mioDispositivo: accetta automaticamente le richieste di autenticazione senza intervento dell'utente.
  • altroCatechista: richiede una conferma esplicita dell'utente tramite dialogo prima che la connessione proceda.
  • Entrambi i dispositivi altroCatechista: richiedono un dialogo di permesso sessione su entrambi i dispositivi prima che la connessione venga accettata.

Protocollo di consenso (double opt-in). Quando entrambi i dispositivi hanno ruolo altroCatechista, _onConnectionInitiated verifica _sessionSyncAllowed prima di accettare la connessione in arrivo. Se il consenso non è stato concesso (l'utente non ha premuto "Procedi"), la connessione viene rifiutata con un messaggio di log. Questo garantisce che entrambi gli utenti debbano premere esplicitamente "Procedi" prima di qualsiasi scambio di dati, implementando un meccanismo di double opt-in.

Correzione propagazione ruolo. _pendingHandshakeRemoteRole viene ora correttamente propagato da _pendingHandshakeData durante il flusso di associazione QR. Questa propagazione avviene in due punti chiave:

  • completePairingAfterQrScan — dopo la scansione e decodifica del QR, il ruolo remoto viene estratto dal payload di handshake e salvato nello stato pendente.
  • _handleReadyForVerification — durante l'handshake di verifica dopo la conferma del pairing code, assicurando che remoteRole sia correttamente salvato nell'associazione P2PDeviceAssociation.

Questa correzione garantisce che il ruolo del dispositivo remoto sia registrato accuratamente nel record di associazione, fondamentale per applicare correttamente l'autorizzazione basata sui ruoli nelle sessioni di sincronizzazione successive.

Dialogo di conferma in _handleAuthResponse. Il dialogo di conferma per i dispositivi altroCatechista ora appare anche quando il dispositivo altroCatechista è l'iniziatore della sincronizzazione. In precedenza, il dialogo appariva solo quando il dispositivo altroCatechista era il ricevente. Questo garantisce un consenso simmetrico: indipendentemente da quale dispositivo avvia la connessione, entrambe le parti vengono invitate a confermare prima che la sessione proceda.

4.2 QR Code Sync

Canale alternativo per dispositivi senza Bluetooth o per trasferimenti one-shot. Implementato in QRDataService:

  • Cifratura: AES-256-GCM con PIN 12 cifre via Random.secure(), valido 3 min (meta createdAt/expiresAt verificata in QRDataService.extractPackageData:263). PBKDF2 350k nuovi / 60k legacy read, AAD CatechHub_Context_QRShare_v1. Indice DB cifrato con PIN di sessione (encryptIndexToChunks/decryptIndexFromChunks:834) — anti-metadata exposure; chunk 1200B con checksum 4 hex, packet checksum 12 hex.
  • Chunking: Payload diviso in chunk JSON di max 1200 byte, ognuno con checksum SHA-256 (prime 4 cifre esadecimali).
  • Integrità: Checksum SHA-256 dell'intero payload (prime 12 cifre hex) verificato dopo il riassemblaggio.
  • Sync differenziale: buildDatabaseIndex() crea un indice per modulo. computeDiffExport() confronta l'indice locale con quello remoto e trasferisce solo i record nuovi/modificati (risoluzione conflitti: local wins).
  • Moduli supportati: Anagrafica, Presenze, Programmazione, Documenti, Note contatto, Catechesi, Annotazioni giornaliere.

4.3 P2P Security Service

Il modulo P2PSecurityService fornisce le fondamenta crittografiche per tutte le comunicazioni P2P:

  • Scambio chiavi — TripleDH + forward secrecy: ogni dispositivo ha coppia X25519 identità long-lived (FlutterSecureStorage p2p_local_keypair) + coppia per-associazione (p2p_assoc_*_privkey); per ogni sessione genera coppia effimera (generateEphemeralKeyPair:487, MAI persistita). Segreto = HKDF(SHA256(h(DH1‖DH2‖DH3‖DH4 ordinati)), salt 0, info CatechHub_P2P_ForwardSecret_v1) + fattore per-associazione opzionale (mixAssociationFactor:915). DH4 = ephemeral↔ephemeral → compromissione futura statiche non espone sessioni passate.
  • Derivazione chiave di sessione: HKDF-SHA256 output 32B, info CatechHub_P2P_Session_v3:<ids>:w<window> + nonce concordato (sorted localNonce+remoteNonce). Sessione valida 30 min (P2PSession.isValid), finestra keep corrente+precedente (_ensureSessionKey:4047).
  • Rotazione: sessionKeyRotation=30min, sessionWindowIndex, timer _sessionKeyRotationTimer + lazy derivation alla prima TX della nuova finestra.
  • Cifratura payload: AES-256-GCM nonce 12B, AAD CatechHub_Context_P2P_v1 (P2PSecurityService:388), wrapper P2PEncryptedPayload:{nonce,ciphertext,mac,alg} (128-bit MAC). Refuso _plaintextAllowedTypes (5 tipi) — tutto il resto scartato se in chiaro.
  • Forward secrecy: vedi TripleDH sopra + chiave di classe per-classe con AAD CatechHub_ClassChannel_v1 (ClassChannelService:85).
  • Pairing code: SAS 6 cifre = SHA256(aux ‖ secret)[0..2] % 1M, aux = nonce concordato + efimere ordinate (P2PSecurityService.computePairingCode:1348); MitM su efimera → SAS diverge, persistito per device (_pairingCodesByDeviceId) across reconnect.
  • Key pinning: publicKeyMatchesAssociation ad ogni riconnessione; se diverge → rifiuto (_handleMessage:2173).
  • Catena di fiducia (solo Responsabile, invariata): Ed25519, validità 30 gg, skew 5 min (_clockSkew), trust root solo chiave pubblica via QR di fiducia, revoche firmate propagate.
  • Associazioni: metadati in Hive trusted_devices_box (toJson senza segreti), segreti (sharedSecret, privKey) solo in FlutterSecureStorage p2p_assoc_*_secret/_privkey (migrazione legacy inclusa, _hydrateSecrets:1140).
  • Seed crittografico: Random.secure() di Dart per nonce e salt.

4.3.1 Canali di sincronizzazione

CatechHub distingue due canali con criteri di protezione diversi:

  • Canale classe (ClassChannelService): cifrato con chiave per-classe AES-256-GCM (blob {v, keyId, sealed} con AAD legato alla classe). I dispositivi "Senza Titolo" ricevono solo blob opachi e fanno da relay: non possono leggere i dati della classe.
  • Canale parrocchiale (ParishChannelService): riunioni e avvisi della rete parrocchiale, scambiati in chiaro tra dispositivi associati per scelta di design: sono comunicazioni "pubbliche" della rete e non contengono dati personali.

5. Security architecture

5.0 Cifratura di campo (FieldEncryptionService — GDPR art.9)

Dati particolari di minori: studentSensitiveFields (field_encryption_service.dart:140) = noteAllergieSalute/allergies/autonomousExits/notes/birthDate/studentPhone/motherPhone/fatherPhone/parentEmail. Formato cieI1: + base64(nonce 12‖ciphertext‖tag), AES-256-GCM, chiave 32B per-dispositivo in registroBox (già cifrato) + deviceKey(): SHA256(seed). Egresso P2P/QR: decryptStudentMapForTransport prima di cifrare col canale (già E2EE); ingresso: encryptStudentMapForStorage prima di persistere (idempotente). Fallimento decifratura → valore in chiaro senza errore (retrocompatibilità).

5.1 Hardware-backed Master Key (AndroidKeyStore) — SecurityManager

A partire dalla versione 2.0, CatechHub richiede esclusivamente protezione hardware per la chiave master di cifratura Hive. Il modulo SecurityManager (singleton in lib/core/security/security_manager.dart):

  • Verifica la presenza di TEE (Trusted Execution Environment) o StrongBox all'avvio tramite local_auth (biometria come proxy TEE) e FlutterSecureStorage (test scrittura/lettura Keystore)
  • Genera la chiave master AES-256 tramite Hive.generateSecureKey() e la custodisce in AndroidKeyStore con encryptedSharedPreferences=true
  • Se TEE/StrongBox non è disponibile, solleva HardwareSecurityException e blocca l'avvio con SecurityBlockScreen — l'app non si avvia su dispositivi senza hardware di sicurezza
  • Nessun fallback software: la chiave master non viene mai memorizzata in memoria volatile o storage non protetto
  • Flusso di inizializzazione: (1) verifica biometrica (local_auth) → proxy TEE, (2) test FlutterSecureStorage → verifica Keystore, (3) generazione/lettura Master Key, (4) creazione HiveAesCipher, (5) marcatura hardware come verificato

Configurazione Android (flutter_secure_storage): encryptedSharedPreferences: true forza l'uso di KeyGenParameterSpec con setIsStrongBoxBacked(true) su API 28+. StrongBox richiede hardware dedicato (Pixel 3+, Samsung S20+), TEE è presente su quasi tutti i dispositivi Android 10+ certificati.

5.5 Registro Trattamenti (audit log HMAC)

In modalità Responsabile ogni operazione rilevante è registrata in un audit log append-only firmato HMAC-SHA256 (AuditLogService): chiave HMAC-SHA256(secret, operatorKey) con segreto in FlutterSecureStorage; payload logId|actionType|timestamp|executorId|entityType|entityId; verifica con confronto constant-time. La UI evidenzia le voci alterate (tamper detection).

5.6 Tombstone e retention (GDPR)

  • Diritto all'oblio: la cancellazione produce un tombstone firmato (payload canonico entityType|entityId|deletedAt|executedBy|..., HMAC-SHA256 con confronto constant-time) propagato a ogni sincronizzazione: impedisce che i dati cancellati "risorgano" da un backup o da un altro dispositivo. In modalità Responsabile solo i dispositivi approvati possono propagarli.
  • Hard delete: cancellazione irreversibile (dati + tombstone dei dati) riservata al Responsabile.
  • Retention automatica: i consensi privacy con scadenza vengono marcati RITIRATO, seguiti da un periodo di grazia di 30 giorni e dalla cancellazione a cascata automatica dei dati (studente, presenze, documenti, note, allegati, record storici).

5.7 Certificate pinning (aggiornamenti)

Il controllo aggiornamenti (UpdateService) usa un HttpClient con certificate pinning SHA-256 per i domini GitHub (api.github.com, github.com, objects.githubusercontent.com): esclusa la trust store di sistema, accettati solo certificati con fingerprint noti; se la lista dei fingerprint è vuota la connessione è fail-closed (mai degradare alla trust store). L'informazione di aggiornamento non contiene dati personali.
